# Real accounts & social backend (Supabase)

Auth and the community feed are backed by a real [Supabase](https://supabase.com) project — Postgres + Auth + Storage. This replaced an earlier fully-mocked version of the same UI (still visible in git history around the "Add Supabase auth + posts/follows schema" commit) and is a genuinely different architecture from the rest of the app: everything else (`useAppStore`, cart/decisions/prices) is still local-only MVP mock data, but auth/social is real, live, and shared across devices/users.

**Setup required before this works**: copy `.env.example` to `.env` and fill in `VITE_SUPABASE_URL`/`VITE_SUPABASE_ANON_KEY` from a Supabase project's Project Settings → API page, then run `supabase/schema.sql` once in that project's SQL Editor (creates `profiles`/`posts`/`post_likes`/`follows`/`auth_rate_limits` tables + RLS policies + the `post-photos` storage bucket + a trigger that auto-creates a `profiles` row on signup). Also deploy the `auth-login` and `auth-password-reset` Edge Functions (see "Rate limiting" below) — sign-in and password reset call them directly and have no client-side fallback. Until `.env` is set, `src/lib/supabase.js`'s `supabase` client is `null` and `isSupabaseConfigured` is `false` — `LoginPanel`/`SocialPage` render a "not configured" message instead of crashing.

**Auth** (`src/hooks/useAuth.js`): `signInWithGoogle`/`signInWithApple` are real `supabase.auth.signInWithOAuth` redirects — each provider must additionally be enabled with real OAuth credentials in the Supabase dashboard (Authentication → Providers) before its button does anything; Apple also needs an Apple Developer account. Email accounts use a real password (`signUpWithPassword`/`signInWithPassword`), not the old passwordless magic-link flow. Session state is **not** stored in `useAppStore`/localStorage-persist, and deliberately not in `localStorage` at all — `src/lib/supabase.js` configures the client with `storage: window.sessionStorage`, so a stolen/replayed value from an XSS payload or a shared machine only lives for the tab's lifetime instead of indefinitely; `useAuth` just subscribes to `supabase.auth.onAuthStateChange` rather than duplicating the token anywhere else.

**Sign-in, sign-up & password reset** (`src/components/LoginPanel.jsx`, `src/components/ResetPasswordModal.jsx`): the sign-in form is native `<form>`/`<input type="email" autoComplete="username">`/`<input type="password" autoComplete="current-password">`/`<button type="submit">`, plus a `type="button"` "Şifreyi göster" visibility toggle and the federated buttons above an "veya" divider — this exact shape (not just the visuals) is what makes password managers recognize and fill the fields, so don't collapse the divider/toggle back into non-`<form>` markup. `username` is mandatory at signup — `LoginPanel` validates the format client-side for a fast error, but the actual enforcement is server-side in `handle_new_user()` (see below), so a direct API call without a username still fails. Password strength is checked with `src/lib/passwordStrength.js` (`getPasswordStrength`/`isPasswordStrongEnough`, no external dependency) and shown live via `PasswordStrengthMeter` in both the signup form and the password-reset modal; the submit button stays disabled below score 2 / under 8 characters. `signInWithPassword` and `requestPasswordReset` don't call the Supabase SDK directly — they invoke the `auth-login`/`auth-password-reset` Edge Functions (see "Rate limiting" below) so throttling can't be bypassed by a client that just skips its own check. Password-reset completion (`ResetPasswordModal`) is a global modal shown whenever `useAuth().passwordRecovery` is true, rather than a route, because Supabase reads its recovery token straight out of `window.location`'s URL fragment on load, which would otherwise collide with `HashRouter` treating `#` as its own route separator.

**Rate limiting** (`supabase/functions/auth-login`, `supabase/functions/auth-password-reset`, `auth_rate_limits` table): both endpoints are proxied through an Edge Function instead of being called from the client directly, so the limit can't be reset by just reloading the page or reading the client bundle. Each function uses the **service-role** client to read/write `auth_rate_limits` (keyed on lowercased email + a purpose tag) and the **anon** client to perform the actual `signInWithPassword`/`resetPasswordForEmail` call; `auth_rate_limits` has no PostgREST policies at all, so it's reachable only from a service-role context (never directly from a browser). `auth-login` allows 5 attempts per email per 15 minutes and clears the counter on a successful login; `auth-password-reset` allows 3 per email per 60 minutes and always returns the same generic message ("Bu e-posta ile bir hesap varsa, şifre sıfırlama bağlantısı gönderildi.") regardless of whether the account exists, is rate-limited, or the email genuinely sent — so neither the response body nor its timing lets an attacker enumerate registered emails. Deploy both with `supabase functions deploy auth-login --no-verify-jwt` / `supabase functions deploy auth-password-reset --no-verify-jwt` (public/unauthenticated endpoints — there's no user session yet at sign-in/reset time).

**Social graph** (`src/hooks/useFollows.js`, `follows` table): `useFollowStats(profileId)` gives real follower/following counts; `useIsFollowing(currentUserId, targetUserId)` backs the per-post "Takip Et" button. This is new — the old mocked version only ever faked the *counts* (`mockSocialStats`), there was no follow relationship or button anywhere in the UI before.

**Community feed** (`src/hooks/useCommunityFeed.js`, `posts`/`post_likes`/`post_comments`/`post_saves` tables, `post-photos` storage bucket): real, shared across every user/device. `CreatePostModal` resizes the photo client-side (max 800px, JPEG ~0.78 quality, same as before) but now uploads the resulting file to Storage instead of embedding it as a base64 data URL in localStorage. Likes are rows in `post_likes` rather than a counter field. `useCommunityFeed`'s `refresh()` does one nested-select query (`posts` joined with `profiles` for the author name, `post_likes` for like rows, `post_comments(count)` for a comment count, and `post_saves` for the current user's own save) rather than a separate query per post per feature — fine at this app's scale, revisit if the feed grows large. Comments (`usePostComments`, one row per comment, publicly readable) are loaded lazily per-post only while a `CommentsModal` is open, not as part of the feed query. Saves (`useSavedPosts`) are **private** — `post_saves`' RLS restricts `select` to `auth.uid() = user_id`, unlike the publicly-readable `post_likes`/`follows`, matching how Instagram treats bookmarks.

**Official recipe posts**: `posts.author_id` is nullable and `posts.recipe_id` exists so all 101 app recipes can be seeded as "official" community posts (`supabase/seed_recipe_posts.sql`, generated from `recipes.json`, run once after `schema.sql` — regenerate it if recipes are added/changed, it's not hand-maintained; it's an *upsert* keyed on `recipe_id`, so re-running it after editing a recipe refreshes that post's title/description/tags/photo in place rather than erroring or duplicating). These posts have `author_id = null`, display as "Tarifim Mutfağı" with a ✓ badge, can't be followed (there's no one to follow), and link to `/recipe/:id` via `recipe_id`; `tags` is copied straight from the recipe's own `tags` array. A client can never insert one of these itself — the `posts` insert RLS policy is `auth.uid() = author_id`, and in Postgres `NULL = NULL` evaluates to `NULL`, not `true`, so a null-`author_id` insert is always rejected via the API. Only a privileged context (the SQL Editor, which runs as `postgres` and bypasses RLS) can create or update one.

**Usernames** (`profiles.username`): mandatory, unique (case-insensitively — `create unique index ... (lower(username))`), format-checked (`^[a-z0-9_.]{3,20}$`) `@handle` that powers the DM "search a username" flow (`useUserSearch`/`NewMessagePage`, an `ilike` search over this column). `handle_new_user()` derives it from `raw_user_meta_data ->> 'username'` (what `signUpWithPassword` sends) for email signups, raising an exception — aborting the signup — if it's missing or blank; OAuth signups (Google/Apple) can't collect one before the redirect, so those get an auto-generated placeholder (`<local-part-of-email>_<id prefix>`) instead, editable later from Settings. Existing rows are backfilled with a `user_<id prefix>` placeholder before the `not null` constraint is applied, so re-running `schema.sql` against a project that predates this column is safe.

**Seeded fake community users**: besides the real account, `profiles` holds ~200 synthetic Turkish accounts (`@example.com` emails, `is_owner = false`) used to populate the feed/comments so the app doesn't look empty pre-launch — these exist directly in the Supabase project (not created by any script in this repo). `supabase/seed_avatars.sql` assigns each of them one of 80 AI-generated realistic photos from `public/images/avatars/avatar_001.webp`–`avatar_080.webp` (Nano Banana 2, varied framing/settings/accessories per the main CLAUDE.md's "Real vs mock data" spirit — these are synthetic people, not real photos, unlike the recipe photos), matched to each name's inferred gender and cycled within that pool since 80 photos cover 200 accounts. `supabase/seed_usernames.sql` similarly assigns each of them a human-looking username derived from their name — a mix of `namesurname`, `namesurname`/`surname` plus a number, `name.surname`, and a handful of out-of-context foodie handles unrelated to the person's name (real social apps have all of these), rather than every fake account looking machine-generated. Run both once in the SQL Editor after the fake profiles exist; re-run to reassign if the pool/style changes. Anon-key writes can't do this directly — `profiles`' update RLS is `auth.uid() = id`, so this has to go through the SQL Editor (or another privileged context) like the other seed scripts here.

**Admin/moderation**: `profiles.is_owner` and `profiles.is_verified` (booleans, both default `false`) drive a 👑 owner badge / ✓ verified badge in `PostCard` and `ProfilePage`, and `is_owner = true` also lets that user delete *any* post via the `posts` delete RLS policy (`auth.uid() = author_id OR` an `is_owner` check), not just their own — the moderation capability the founder account needs. Both flags are grantable **only** from a privileged context (SQL Editor) — never via the app — enforced by the `protect_privileged_profile_fields` trigger on `profiles`, which silently resets both columns back to their stored value on any `UPDATE` where `auth.role() = 'authenticated'` (i.e. a normal logged-in client request). Without that trigger, the existing "users can update their own profile" policy would let any user grant themselves both flags via a plain client-side `update`. To grant them: `update public.profiles set is_owner = true, is_verified = true where email = '...'` in the SQL Editor.

If you touch this area: `supabase/schema.sql` is meant to be re-run safely (every statement is `create if not exists` / `drop policy if exists` + recreate, or a bare `alter table` that's a no-op the second time), so prefer editing it in place and re-running over hand-editing tables in the dashboard.
